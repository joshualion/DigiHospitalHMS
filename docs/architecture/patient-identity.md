# Patient Identity Architecture

Date: 2026-08-23

Phase 2A adds hospital-scoped patient identity records only. It does not add appointments, queues, encounters, billing, laboratory, pharmacy, admissions or patient merging.

## Data Model

- `patients` stores the hospital number, registration facility, registering staff user, demographics, contact fields, and record state.
- `patient_identifiers` stores optional identifiers such as NIN, NHIS, legacy MRN or clinic IDs. NIN remains optional.
- `patient_contacts` stores ordinary contacts and next of kin.
- `patient_allergies` and `patient_alerts` store important identity/clinical-safety warnings with recorder, severity, status and timestamps.
- `patient_activity_events` provides the patient-profile timeline foundation.

Patient records are scoped by `hospital_id`. Hospital numbers are unique per hospital and generated by `NumberSequenceService` from the `patient_number` sequence using `lockForUpdate()`.

## Sensitive Search

Phone, email and identifier values are not searched as plaintext. The application stores:

- encrypted display value using Laravel `Crypt`;
- deterministic HMAC-SHA256 lookup hash using `APP_KEY`;
- normal names and hospital numbers as ordinary indexed fields.

Trade-off: HMAC lookup supports exact searches for phone/email/identifier values but not partial matching. Name and hospital-number search remain partial. Rotating `APP_KEY` would require re-hashing lookup columns.

## Duplicate Detection

Duplicate detection is warning-only and never merges records. Current configurable signals are:

- phone hash;
- first name + last name + date of birth;
- first name + last name + estimated age when DOB is absent;
- approved/searchable identifier hash.

Settings are read from `hospital_settings.operating_preferences.patient_duplicate_matching`. Registration/update is blocked until the user explicitly acknowledges duplicate warnings.

## Record State

Patients can be `active`, `archived` or `deceased`. Transitions are policy-controlled and audited. No hard-delete route exists.

## Authorization

Patient routes are admin-area routes, but are available to authorized administrative, reception, nursing and medical roles. Policies enforce `patients.view`, `patients.register`, `patients.update`, `patients.archive` and `patients.record-alerts`.

## Deferred

Patient documents and photographs are deferred until a private storage disk, malware scanning and access logging are designed. Patient merge, appointments and all clinical modules remain out of Phase 2A.
